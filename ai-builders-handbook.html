Chapter 1: Memory, names, the stack and the heap

Volume 1: Python memory and core mechanics

1.1 What a program is

A program is a list of instructions the computer follows one at a time, plus the data those instructions work on. The computer keeps that data in memory (also called RAM).

Picture memory as an enormous warehouse of numbered shelves. Each shelf has a number, called its address. Something you want to keep goes on a shelf; to use it later you need to know which shelf. When the program ends, the warehouse is cleared.

Everything Python does comes down to four moves:

  • put a piece of data into memory,
  • remember where you put it,
  • look at it or change it,
  • throw it away when nobody needs it.

This chapter is about those four moves. Get them right and most later topics (mutability, closures, generators, async, agent state) become variations on a theme you already understand.

1.2 Objects: everything is a thing in memory

In Python, every piece of data is an object. A number is an object. A piece of text is an object. A list is an object. Even a function is an object. Each object has three properties:

  • Identity: which shelf it sits on. It never changes for the life of the object.
  • Type: what kind of thing it is (number, text, list).
  • Value: what it currently contains.

You can ask Python for all three:

price = 250
print(type(price))   # <class 'int'>  -> the type
print(id(price))     # a big number      -> the identity (in CPython, its memory address)
print(price)         # 250               -> the value

You will almost never call id() in real work. It is a flashlight for learning: it lets you check whether two names point at the same object.

1.3 Names are labels, not boxes

Most people picture a variable as a box with a value inside. In Python that picture is wrong, and the wrong picture causes real bugs. The right picture:

Mental model

A variable is a name tag (a label). The object sits on a shelf. The name tag points to the shelf. Assigning with = means "stick this label on that object". It never copies the object.

So price = 250 does two things: it creates the object 250, then attaches the label price to it. Now watch what a second label does:

a = [1, 2, 3]     # create a list object, stick label a on it
b = a             # stick a second label b on the SAME object. No copy.
c = [1, 2, 3]     # create a NEW list object with equal contents, label c

print(a == b)     # True   same value
print(a is b)     # True   same object
print(a == c)     # True   same value
print(a is c)     # False  different objects that happen to look alike

Two comparison tools, two different questions. == asks "do these have the same value?" is asks "are these literally the same object?" Twins are ==. One person with two nicknames is is.

1.4 The heap: where objects live

The heap is the big open area of memory where all objects are stored. It has no tidy order. What matters is how long things stay there:

Rule of the heap

An object stays alive as long as at least one label (or container) points to it. When the last pointer goes away, Python frees the object.

Python tracks this with a reference count: every object carries a tally of how many things point at it. A new label adds one. Removing a label subtracts one. At zero, the object is deleted on the spot.

import sys
data = [10, 20, 30]
alias = data
print(sys.getrefcount(data))   # 3, not 2: passing it to the function adds one temporary reference
del alias                      # remove one label
print(sys.getrefcount(data))   # 2

Containers hold pointers too. A list does not contain its items the way a bag contains apples. It holds a row of pointers to objects elsewhere on the heap. The list [10, 20, 30] is one object holding three arrows. This is why a list can hold different types, and why two lists can share an item. It also matters a great deal in Chapter 2.

(Rarely, objects point at each other in a circle and their counts never reach zero. Python runs a separate cleanup, the garbage collector, to catch those. For now, reference counting is the picture to keep.)

1.5 The call stack: the workspace for each function call

A function call is a small errand. When Python starts one, it creates a frame: a private workspace that holds that call's local names and remembers which line it is on. Frames are stacked like plates: a new call goes on top, and the top plate is always the one being worked on. This is the call stack, and it works last-in, first-out.

  • Function A calls function B: B's frame goes on top of A's.
  • B finishes (returns): B's frame is removed and all its local names disappear.
  • Control drops back to A, exactly where it left off.

The key sentence of this chapter: names live in frames; objects live on the heap; names point at objects. When a frame disappears, its names disappear, and each object loses one pointer. Objects that lose their last pointer are freed. Objects someone else still points at survive.

A note on accuracy

The stack-and-heap picture is the standard mental model and it predicts Python's behavior correctly. The exact machinery in CPython (the standard Python) is more detailed. For example, names at the top level of a file live in a dictionary that lasts the whole program, so the bottom "module" frame is a simplification. Also, small integers (from -5 to 256) and some short strings are pre-made and shared, so they are never freed. None of this changes how you should reason about your code.

Reading a traceback is reading the stack

When Python crashes, it prints the call stack for you. Read it from the bottom up: the last line is the error, the line above it is where it happened, and the lines above that show how you got there.

Traceback (most recent call last):
  File "app.py", line 12, in <module>        # bottom frame: the file itself
    build_report(data)
  File "app.py", line 8, in build_report      # called by the frame above
    total = compute_total(rows)
  File "app.py", line 3, in compute_total     # top frame: where it crashed
    return sum(r["amount"] for r in rows)
KeyError: 'amount'                            # what went wrong

That is a picture of the stack at the moment of failure: <module> called build_report, which called compute_total, which hit a row with no "amount" key.

1.7 The big consequence: sharing and mutation

Because assignment copies pointers, not objects, two names can point at one object. If the object can be changed, everyone holding a pointer sees the change.

def add_bonus(scores):
    scores.append(100)      # changes the object that scores points at

marks = [90, 85]
add_bonus(marks)
print(marks)                # [90, 85, 100]  the caller sees the change

When add_bonus(marks) runs, a new frame is created and its name scores is attached to the same list that marks points to. There is one list and two labels in two different frames. Changing the list through either label changes it for both. Nothing was copied.

Now compare with re-pointing a label:

def replace(scores):
    scores = [1]            # moves the local label to a brand-new list

marks = [90, 85]
replace(marks)
print(marks)                # [90, 85]  untouched

Here the function did not change the list. It moved its own label onto a different object. The caller's label never moved. The whole distinction between changing an object (mutation) and moving a label (rebinding) is the subject of Chapter 2, and it explains a large share of surprising Python behavior.

1.8 Reading real code with this lens

Here is the kind of code you will meet in production: a small cache that avoids reloading expensive reports.

class ReportCache:
    def __init__(self):
        self._store = {}

    def get(self, key, loader):
        if key not in self._store:
            self._store[key] = loader(key)
        return self._store[key]

cache = ReportCache()

You do not need to know what a class is yet. Ask the three questions:

  1. What objects are created? One ReportCache object (from ReportCache()), one dictionary inside it ({}), and, on every new key, whatever loader(key) returns.
  2. What points at them? The module-level name cache points at the cache object. The cache object points at the dictionary through _store. The dictionary points at every loaded report.
  3. When are they freed? The report objects are freed when the dictionary stops pointing at them. But nothing here ever removes an entry. And cache lives at module level for the whole program.

Conclusion, without running anything: every report ever loaded stays in memory until the program exits. In a long-running service this is a classic memory leak. That is not syntax knowledge; it is the three questions applied to a dozen lines. Real fixes (a size limit, an expiry, weak references) all follow from the same picture.

1.10 Check yourself

Try to answer before you open each one.

If two functions' frames each hold a name pointing at the same list, and one function appends to the list, does the other function see it?

Yes. There is one list object on the heap and two labels pointing at it. An in-place change through either label is visible through both.

What does this print? x = [1, 2], then y = x, then y = [3], then print(x)

[1, 2]. The line y = [3] creates a new list and moves the label y onto it. It does not touch the original list, which x still points at.

True and False. Two separate list objects with equal contents.

Chapter 2: Pass-by-assignment, mutable and immutable objects

Volume 1: Python memory and core mechanics

Chapter 1 gave you the picture: names are labels, objects live on the heap, frames hold names, and an object lives as long as something points at it. This chapter puts that picture to work on the question that causes more Python confusion than any other:

The question

When I hand something to a function, can the function change my original? Sometimes yes and sometimes no, and it can feel random. It is not random. Two ideas explain every case: how the object is handed over, and whether that kind of object can be edited at all.

2.1 How arguments are handed over: pass-by-assignment

Programming languages tend to use one of two conventions for handing data to a function:

  • Pass by value: the function gets a photocopy. Whatever it does to the copy, your original is safe.
  • Pass by reference: the function gets your actual variable. It can even repoint your variable to something else.

Python does neither. It does exactly what a plain assignment would do:

Mental model

Calling f(x) is the same as writing parameter = x inside a fresh frame. The parameter is a new label stuck onto the same object your own name points at. No copy is made, and the function cannot move your label.

This convention is called pass-by-assignment (you will also see "pass by object reference" or "call by sharing"). When a call happens, Python does four things:

  1. Looks at each argument and finds the object it refers to.
  2. Creates a new frame on the call stack.
  3. For each parameter, attaches the parameter's name to the matching object. Nothing is copied.
  4. Runs the function body inside that frame.

The consequence is that the caller and the function now share the object. Inside the function there are only two things you can do with a parameter, and they behave completely differently:

  • Mutate the object (edit it in place). Everyone who points at it sees the change, the caller included.
  • Rebind the name (move the parameter's label onto another object). That only moves the function's own label. The caller never notices.

Whether mutation is even possible depends on the object. That is the second idea.

2.2 Mutable and immutable objects

An object is immutable if it can never be edited after it is created. Its value is fixed for life. An object is mutable if it can be edited in place: same object, same identity, new contents.

Immutable (cannot be edited)Mutable (can be edited in place)
int, float, bool, complexlist
str (text), bytesdict
tuple, frozenset, rangeset, bytearray
NoneInstances of classes you or a library define (by default)

Use id() from Chapter 1 to see the difference with your own eyes:

n = 1000
print(id(n))
n = n + 1
print(id(n))          # a DIFFERENT id: 1001 is a new object; the old 1000 was not touched

items = ["a", "b"]
print(id(items))
items.append("c")
print(id(items))      # the SAME id: one object, edited in place

Text is the case that surprises people most, because it feels editable:

name = "alice"
name[0] = "A"                 # TypeError: 'str' object does not support item assignment
name = "A" + name[1:]         # works, but builds a NEW string and moves the label
print(name.upper())           # also builds a new string; name itself is unchanged

Two clarifications that save real confusion:

  • "Immutable" describes the object, never the name. A name can always be moved to point somewhere else. What you cannot do is edit the object it pointed at.
  • Never use is to compare numbers or text. Python sometimes reuses equal immutable objects (small numbers, some strings) and sometimes does not, so is can give answers that vary between runs and versions. Use == for values. Use is for None and for asking "the very same object?".

The rule

The caller sees a change only when the function mutates an object that both sides can reach. Rebinding a name never crosses the frame boundary.

2.4 Two kinds of +=

Here is a detail that separates people who have memorized rules from people who have a mental model. Both snippets below add 3 to a list, and they behave differently:

a = [1, 2]
b = a
a = a + [3]        # builds a NEW list [1, 2, 3], then moves label a onto it
print(b)           # [1, 2]      b still points at the old list

a = [1, 2]
b = a
a += [3]           # asks the list to extend ITSELF, in place
print(b)           # [1, 2, 3]   same object, so b sees it

The rule: a += x first offers the object a chance to update itself in place. Lists accept, so the same list is edited. Numbers and text cannot be edited, so Python falls back to a = a + x: a new object, and the label moves. So += on a number is always a rebinding, while += on a list is a mutation. When you see += applied to a function parameter, check what type it is, because it may be quietly changing the caller's data.

2.5 Immutability is shallow

Chapter 1 established that a container holds pointers to objects, not the objects themselves. That matters here. A tuple is immutable, which means its row of pointers can never be changed: no pointer can be added, removed or re-aimed. It says nothing about the objects at the other end of those pointers.

record = ("Q3", [10, 20])
record[1].append(30)         # works: we edited the LIST; the tuple's pointers are unchanged
print(record)                # ('Q3', [10, 20, 30])
record[0] = "Q4"             # TypeError: a tuple's pointers cannot be re-aimed

So "this tuple is immutable" is a weaker promise than it sounds if the tuple holds mutable objects. Only when everything reachable is immutable is the whole structure truly frozen.

Why the distinction exists: dictionary keys

A dictionary finds entries by computing a fingerprint (a hash) from the key's value and using it to decide where to store the entry. If a key could change after being stored, its fingerprint would change and the dictionary would look in the wrong place and lose the entry. So Python only allows hashable objects as keys, which in practice means immutable ones:

prices = {("AAPL", "NASDAQ"): 190}     # fine: a tuple of text is immutable
prices = {["AAPL", "NASDAQ"]: 190}     # TypeError: unhashable type: 'list'

Immutability also makes sharing safe: many names can point at one immutable object with no risk that one holder changes it under another's feet. That is why Python can reuse small numbers and strings freely.

2.6 Copying: alias, shallow copy, deep copy

Because b = a does not copy, Python gives you separate tools for real copies. There are three levels, and confusing them is a top source of bugs:

OperationWhat is createdInner objects
b = a (alias)Nothing. A second label.All shared
a.copy(), list(a), a[:], dict(a) (shallow copy)A new outer containerShared with the original
copy.deepcopy(a) (deep copy)A new outer container and new copies of everything insideNot shared
 
import copy
a = [[0], [0]]
alias   = a                    # same list

Open the fifth scenario tab ("Shallow copy") in the trace above to watch a shallow copy share its rows with the original. A shallow copy protects you from changes to the outer list (adding or removing rows) but not from edits to the rows themselves.

A classic trap: the shared row

grid = [[0] * 3] * 3          # WRONG
grid[0][0] = 1
print(grid)                   # [[1, 0, 0], [1, 0, 0], [1, 0, 0]]  all rows changed!

grid = [[0] * 3 for _ in range(3)]   # RIGHT

Why? [row] * 3 repeats the pointer, not the row: one row object, three arrows pointing at it. Changing "row 0" changes the only row there is. The second version runs the expression [0] * 3 afresh on every pass, so it creates three separate rows. (List comprehensions like this get their full explanation in Chapter 6.)

2.7 The default-argument trap

This is the single most-quoted Python gotcha, and the mental model explains it completely. Consider:

def add(item, bucket=[]):
    bucket.append(item)
    return bucket

a = add(1)
b = add(2)
print(a)        # [1, 2]   surprise: we never put 2 in a's list
print(b)        # [1, 2]
print(a is b)   # True     it is one list

The key fact: the def line runs once, when the function is defined, and default values are created at that moment. Python builds the empty list one time and stores it on the function object. Every later call that omits bucket attaches the parameter to that same stored list. You can see it:

print(add.__defaults__)    # ([1, 2],)  the stored default, now holding our data

The fourth scenario in the trace above ("Default argument trap") walks through this. The fix is to use None as a signal meaning "no value given" and create the list inside the function, so each call gets a fresh one:

def add(item, bucket=None):
    if bucket is None:
        bucket = []          # created on EVERY call, inside the frame
    bucket.append(item)
    return bucket

None is the right placeholder because it is immutable and cannot be confused with real data. Reading rule: whenever you see =[], ={} or =set() in a function signature, stop. It is either a bug or deliberate (a memoization cache, say) and you should find out which. Immutable defaults (0, "text", None, ()) are always safe.

2.8 The mutation radar: what changes things and what does not

To read code fluently you need to spot mutation quickly. These operations change the object they are applied to:

TypeMutates in place
listappend, extend, insert, remove, pop, sort, reverse, clear, x[i] = v, del x[i], +=
dictupdate, pop, setdefault, clear, d[k] = v, del d[k]

And these produce new objects and leave the original alone: sorted(x), x + y, slices like x[1:], {**a, **b}, list comprehensions, and every method on a string or a tuple.

There is a helpful convention behind the names: methods that mutate in place usually return None, while functions that build a new object return that object. Compare items.sort() (edits the list, returns None) with sorted(items) (returns a new sorted list). This produces a famous bug:

nums = [3, 1, 2]
nums = nums.sort()       # sort() edited the list and returned None, then we moved nums onto None
print(nums)              # None

2.9 Reading real code: the config that remembers

Here is a bug shape that appears in real services. Do not run it. Read it with the three questions from Chapter 1, plus the sharing rule from this chapter:

DEFAULTS = {"retries": 3, "timeout": 30}

def make_config(overrides):
    cfg = DEFAULTS
    cfg.update(overrides)
    return cfg

a = make_config({"timeout": 5})
b = make_config({})
print(b["timeout"])
  1. What objects exist? One dictionary, DEFAULTS, created at module level. The function creates no dictionary of its own.
  2. Who points at it? DEFAULTS (module level), and inside each call cfg, which is attached with a plain assignment. That is a second label, not a copy.
  3. What does the body do to it? cfg.update(overrides) is on the mutation radar. It edits the one shared dictionary.
  4. How long does it live? The whole program, because DEFAULTS is module-level.

Conclusion: the first call permanently rewrites the defaults. b["timeout"] prints 5, not 30, and a and b are even the same object. In a real service this shows up as "settings leak between requests", and it is very hard to debug if you do not think in pointers. The fix makes a new dictionary each call:

def make_config(overrides):
    return {**DEFAULTS, **overrides}      # builds a new dict: DEFAULTS is untouched

Caveat, from section 2.6: this is a shallow copy. If the values inside DEFAULTS were themselves lists or dictionaries, they would still be shared, and you would use copy.deepcopy instead.

This exact question returns in Volume 7. When an agent workflow passes a state dictionary from one step to the next, a bug like "step 3 changed something step 1 was still using" is nearly always this chapter: did that step edit the shared object, or return a new one?

2.10 Three function styles, and how to tell which one you are reading

  • Pure style: reads its inputs, builds and returns a new result, changes nothing else. Easy to reason about and safe to call anywhere. sorted() is one.
  • In-place style: edits what it is given and returns None. list.sort() is one. Fine when documented, and the None return is a useful signal.
  • Mixed style: edits the input and returns it, or edits an input while also returning something new. This is where callers get confused, because it is unclear whether they now hold a new object or the old one.

When you read a function, decide which style it is. When you write one, pick a style and stick to it. A function that silently mutates its arguments is a surprise to whoever calls it.

2.11 The checklist for reading any function

  1. What does each parameter point to, and is that type mutable or immutable?
  2. Does the body mutate a parameter (radar methods, item assignment, +=) or just rebind it?
  3. Does it return a new object, or the same one it was given?
  4. Is there a mutable default value (=[], ={}) or a module-level object being touched?
  5. Who else holds a pointer to the object being changed?

2.13 Check yourself

Predict each answer before opening it.

def f(x): x = x + [1]. You call f(a) with a list a. Does a change?

No. x + [1] builds a new list and x = ... moves the local label onto it. The list a points at is untouched.

def f(x): x += [1]. Same call. Does a change?

Yes. For lists += extends the list in place, and x and a point at that one list.

def f(x): x += 1 called with an integer variable n. Does n change?

No. Integers cannot be edited, so Python builds a new integer and moves only the local label x.

t = (1, [2]). Does t[1].append(3) work? What is t afterwards?

It works. t becomes (1, [2, 3]). The tuple's pointers did not change; the list at the end of one pointer was edited.

What does grid = [[0] * 2] * 2, then grid[0][0] = 5, then print(grid) show?

[[5, 0], [5, 0]]. The outer list holds two pointers to the same single row object.

Why is def track(seen=set()) dangerous?

The set is created once, when def runs, and stored on the function object. Every call that omits seen shares and modifies that same set, so state leaks between calls. Use seen=None and create the set inside.

What is nums after nums = [3, 1, 2] then nums = nums.sort()?

None. sort() edits the list in place and returns None, and the assignment moved nums onto that None.

a = [1], b = a.copy(), b.append(2). What is a?

[1]. The copy is a separate list, and nothing inside it is shared because the items are plain numbers. With nested mutable items, editing an inner item through b would show up in a.

Chapter 3: Scopes (LEGB) and execution frames

Volume 1: How Python thinks

Chapters 1 and 2 were about objects and the labels pointing at them. This chapter is about the labels themselves: when you write a name, where does Python look for it, and where does an assignment put it? Get this wrong and you meet NameError, UnboundLocalError, functions that quietly ignore your global, and variables that "changed by themselves". Get it right and you can trace any name in any file back to where it came from.

3.1 One name, many meanings

x = "global"

def show():
    x = "local"
    print(x)

show()        # local
print(x)      # global

There are two different labels both spelled x. Python keeps them apart because each lives in a different namespace. The rest of the chapter is the rulebook for which namespace is used when.

3.2 Namespaces: a dictionary of names

Mental model

A namespace is a table (in fact, a Python dictionary) whose keys are names and whose values are pointers to objects. "Assigning a name" means writing a row into a namespace. "Using a name" means looking a row up.

You can look at these tables directly:

score = 10
print(globals()["score"])      # 10  the module-level table

def f():
    a = 1
    b = 2
    print(locals())            # {'a': 1, 'b': 2}  this call's own table
f()

This sharpens Chapter 1. There we said "names live in frames". More exactly, each function call has its own local namespace, the file itself has a global namespace that lasts as long as the program, and Python's built-in names live in a third one. A frame is the workspace that ties these tables to a position in the code.

3.3 The LEGB rule

When code uses a name, Python searches four layers in a fixed order and stops at the first match:

LayerWhat it isLifetime
LocalNames created inside the current function callUntil that call returns
EnclosingLocal names of any function this one is nested insideAs long as the inner function is alive
GlobalNames at the top level of the current file (module)The whole program
Built-inNames Python provides everywhere: print, len, range, ValueError…The whole program

If no layer has the name, Python raises NameError. The search always goes outward: an inner function can see the layers around it, but an outer layer can never see into an inner function's locals.

3.4 What creates a scope, and what does not

New scopes are created by: a function (def or lambda), a class body, a comprehension (list, dict, set, generator), and the module itself. Notably, these do not create a scope: if, for, while, with, try. Indentation makes a block, not a scope.

for i in range(3):
    last = i * 10
print(i, last)         # 2 20   both still exist: a loop is not a scope

if True:
    flag = "set inside if"
print(flag)            # works

squares = [k * k for k in range(3)]
print(k)               # NameError: k lived only inside the comprehension

Reading consequence: a name first assigned inside a loop or an if is visible for the rest of the function. That is convenient and also a source of bugs (a loop variable still holding its last value long after the loop).

3.5 Watch names being looked up

The illustration shows the four layers, innermost first. When a name is used, the layers are checked in order: amber means "searched, not found", green means found, dashed means never reached. Try each tab.

3.6 An assignment anywhere makes the name local everywhere

This is the rule that produces the most confusing error in the chapter:

count = 0

def bump():
    count = count + 1      # UnboundLocalError: local variable 'count' referenced before assignment

bump()

You might expect Python to read the global count, add one, and create a local. It does not work that way. Before the function ever runs, Python scans its whole body. If a name is assigned anywhere in it, that name is local for the entire function. So on the right-hand side, count means "the local count", which has no value yet. The global one is never consulted. The third tab in the illustration walks through it.

What counts as an assignment here: x = ..., x += ..., for x in ..., import x, def x, with ... as x, except ... as x. All of these bind a name, so all of them make it local.

3.7 global and nonlocal: rebinding outer names

To rebind (not merely read) a name that lives in an outer scope, you must declare where it lives:

count = 0
def bump():
    global count           # "count means the module-level one"
    count = count + 1

def make_counter():
    n = 0
    def inc():
        nonlocal n         # "n means the enclosing function's one"
        n += 1
        return n
    return inc

Now connect this to Chapter 2. There is a difference between reading, mutating and rebinding, and only the last needs a declaration:

Inside a function you want to…ExampleNeeds global/nonlocal?
Read an outer nameprint(rate)No
Mutate the object an outer name points atregistry.append(x), cfg["a"] = 1No: no label is moved
Point an outer name at a different objectcount = count + 1, registry = []Yes

Heavy use of global is usually a design smell, because any function can now change program-wide state. When you see it in code, note it: it marks a place where state escapes the function.

3.8 Shadowing built-ins

Because assignment writes into the local or global table, you can accidentally hide a built-in by reusing its name:

list = [1, 2, 3]           # the global name "list" now hides the built-in list type
print(list("abc"))         # TypeError: 'list' object is not callable

The lookup found your list in the Global layer first and never reached Built-in. The usual offenders: list, dict, set, str, id, type, input, max, min, sum, len, filter. When you meet a baffling "is not callable" error, check whether a variable stole a built-in's name. Delete it with del list and the built-in reappears.

3.9 Names are resolved when the code runs

Python looks up a name at the moment the line executes, not when the function is written:

rate = 0.1
def price(x):
    return x * (1 + rate)

rate = 0.2
print(price(100))          # 120.0  price sees the CURRENT rate

This is called late binding. It explains a famous trap:

fns = [lambda: i for i in range(3)]
print([f() for f in fns])          # [2, 2, 2], not [0, 1, 2]

fns = [lambda i=i: i for i in range(3)]
print([f() for f in fns])          # [0, 1, 2]

Each lambda contains the name i, not its value at creation time. When they run later, they all look up i in the enclosing scope, where it has ended at 2. The fix uses a default argument (i=i), which, as Chapter 2 showed, is evaluated once, right when each lambda is created, and stored. Chapter 11 explains the machinery underneath (cell objects).

3.10 Frames in full, and why recursion works

Now that you know about namespaces, here is what a frame is made of:

  • the code being executed and a marker for the current line,
  • its own local namespace,
  • a link to the global namespace of the file the function was defined in,
  • a link to the built-in names,
  • a link back to the caller's frame.

That last link is the call stack, and it is how a traceback (Chapter 1) is produced: follow the chain of "who called me". Because every call gets a new frame with its own locals, the same function can be active many times at once without the calls interfering. That is exactly what recursion is. Notice that three separate variables named n exist at once (3, 2 and 1), each in a different frame. They do not conflict. Also notice the frames pile up waiting; Python limits the depth (about 1000 by default) and raises RecursionError beyond it, to stop a runaway function from consuming all memory.

3.11 Reading real code: where does each name come from?

A pattern you will see constantly: a module with shared state and small functions.

_handlers = {}
LOG_LEVEL = "INFO"

def register(name):
    def wrap(fn):
        _handlers[name] = fn
        return fn
    return wrap

def set_level(level):
    LOG_LEVEL = level

Resolve every name with LEGB:

  • In wrap, _handlers is not local and not in register's locals, so it is found in Global. The line _handlers[name] = fn mutates the dictionary; no rebinding, so no global declaration is needed. name is found in Enclosing (register's parameter). fn is local to wrap.
  • In set_level, LOG_LEVEL = level is an assignment, so LOG_LEVEL is a new local. The module-level LOG_LEVEL is untouched. This function does nothing useful: a silent bug. The fix is global LOG_LEVEL, or better, keeping settings in an object or dictionary and mutating that.

That two-question routine (which layer? read, mutate or rebind?) resolves any name in any file.

Which layer supplies each name in print(len(items)) inside a function where items is a parameter?

UnboundLocalError. The assignment total = 9 makes total local to f for the whole body, so the print line reads a local that has no value yet.

No. append mutates the list; it does not rebind the name. global is only needed to point the name at a different object.

[2, 2, 2]. Each lambda looks up i when called, and by then i has reached its final value, 2. Use lambda i=i: i to capture each value at creation.

Chapter 4: Data types and operators

Volume 2: The core language, properly

Volume 1 taught you how Python holds things. Volume 2 teaches the language itself, always through the same lens. This chapter asks: what kinds of objects exist, and what does an operator like + or == actually do? The answer to the second question is the key to reading unfamiliar code, because in Python an operator is not fixed magic. The objects decide what it means.

4.1 Names have no type; objects do

From Chapter 1: a name is a label and an object is the thing. The type belongs to the object.

x = 5              # x points at an int object
x = "five"         # now x points at a str object. Perfectly legal.
print(type(x))     # <class 'str'>
print(isinstance(x, str))   # True

Python is dynamically typed (a name can point at anything at any moment) and strongly typed (it will not silently mix incompatible objects: "5" + 1 is an error, not 6 or "51"). Both facts matter when you read code: you cannot tell what a name holds from the name, so you look for where it was bound, and Python will complain loudly, at run time, if two types do not fit.

4.2 Numbers

Integers (int) have no size limit. Python grows them as needed, so there is no overflow: 2 ** 200 just works. Floats (float) are decimal-looking numbers stored in binary, with a fixed precision (about 15-16 significant digits).

print(2 ** 100)            # 1267650600228229401496703205376  exact
print(0.1 + 0.2)           # 0.30000000000000004
print(0.1 + 0.2 == 0.3)    # False

Why the float surprise? Computers store floats in base 2, and 0.1 has no exact base-2 form, just as 1/3 has no exact decimal form (0.3333…). What is stored is the nearest representable value. Every language using standard floats behaves this way; it is not a Python bug.

Rule of thumb

Never compare floats with ==: use math.isclose(a, b). For money, use decimal.Decimal (exact decimal arithmetic) or store integer cents. Floats are for measurements and estimates.

Division and rounding have a few rules worth knowing cold:

4.3 Text: str and bytes

A str is an immutable sequence of Unicode characters. Being a sequence, you can index and slice it, and because it is immutable (Chapter 2), every "edit" builds a new string.

s = "hello"
print(s[0], s[-1], s[1:4])     # h o ell     index, last, slice (a new string)
print(len(s), "ell" in s)      # 5 True
name = "Asha"
print(f"Hi {name}, 2 + 2 = {2 + 2}")   # f-string: expressions inside braces are evaluated

Text and bytes are different worlds. Computers store and transmit bytes; a string is what you get after decoding bytes with an encoding (almost always UTF-8):

word = "caf\u00e9"
print(len(word))                    # 4 characters
data = word.encode("utf-8")
print(data, len(data))              # b'caf\xc3\xa9' 5   the é takes two bytes
print(data.decode("utf-8"))         # café

You will meet this again in Chapter 9 (files) and Chapter 25 (network responses arrive as bytes). Rule: decode bytes to text at the edge of your program, work in text inside, encode again on the way out.

One more performance habit: because strings are immutable, s += piece in a long loop creates a new string each time. Build a list of pieces and use "".join(pieces) once.

4.4 Booleans, truthiness, and what and/or really return

True and False are the two bool objects (and, historically, bool is a kind of int, so True + True == 2). More important is truthiness: any object can be used in an if, and Python decides whether it counts as true.

The falsy list (memorize this; everything else is truthy)

False, None, zero of any numeric type (0, 0.0), and empty containers: "", [], (), {}, set(), range(0).

This is why if items: is the standard way to say "if the list is not empty". Two traps to remember: the string "0" and the string "False" are truthy (non-empty strings), and a custom object is truthy unless its class says otherwise.

Now the part that surprises everyone. and and or do not return True or False. They return one of their operands, and they stop early (short-circuit):

print(0 or "default")        # default   or: first truthy operand, else the last
print("a" or "b")            # a         stops at the first truthy one; "b" is never looked at
print(0 and "x")             # 0         and: first falsy operand, else the last
print("a" and "b")           # b

name = user_name or "guest"  # common idiom: use a default if empty

The idiom hides a bug: timeout = user_timeout or 30 replaces a legitimate 0 with 30, because 0 is falsy. When zero or an empty string is a valid input, write 30 if user_timeout is None else user_timeout.

4.5 None

None is a single, special object meaning "no value here". There is exactly one, so identity checks are correct and idiomatic: if x is None. Any function that finishes without a return hands back None, which is why result = my_list.sort() (Chapter 2) gives None.

4.6 Comparison and equality

print(1 < 5 < 10)             # True   chained: means (1 < 5) and (5 < 10)
print(1 == 1.0)               # True   equal values, different types
print("a" < "b")               # True   text compares by character order
print(3 < "4")                # TypeError: no ordering between int and str
d = {1: "int key"}
d[1.0] = "float key"          # 1 and 1.0 are equal AND hash alike, so this OVERWRITES key 1
print(d)                      # {1: 'float key'}

Recall from Chapter 1: == asks about value, is asks about identity. Ordering comparisons (<, >) require the two objects to know how to compare with each other.

4.7 Operators are method calls in disguise

Here is the idea that makes the language coherent. When Python sees a + b, it does not have addition built into the symbol. It asks the objects:

Mental model: operator dispatch

1. Ask the left object: call type(a).__add__(a, b).
2. If it answers NotImplemented ("I don't know how to add that"), ask the right object through its reflected method, type(b).__radd__(b, a).
3. If both decline, raise TypeError.

So + adds numbers because int defines it that way, joins text because str defines it that way, and joins lists because list does. The same is true of == (__eq__), len(x) (__len__), x[i] (__getitem__) and if x: (__bool__, falling back to __len__). Step through a few cases:

In library code, a | b, a & b, a >> b and a / b can mean anything the author defined: | merges dictionaries, / joins file paths (Path("a") / "b.txt"), and LangChain-style libraries use | to chain pipeline steps. The symbol is just a call. You will define your own operators in Chapter 16.

4.8 Converting between types

Python converts explicitly. The one implicit conversion you will see is numeric: mixing int and float gives a float.

4.9 Reading real code: the config that is always on

import os

Apply the chapter. What type does each name hold? Environment variables are always strings (Chapter 9 covers why). So:

  • If the operator sets DEBUG=false, DEBUG is the string "false", which is non-empty and therefore truthy. Debug tools switch on in exactly the situation the person meant to turn them off. If DEBUG is unset, it is the boolean False: two different types from one line.
  • PORT is the string "9000" when set and the integer 8000 when not. Code that later does arithmetic on it works in one case and raises TypeError in the other.

Real programs juggle many values at once, and Python offers four built-in ways to hold them. Chapter 1 gave you the essential fact: a container holds pointers to objects, not the objects themselves. This chapter shows how each of the four containers arranges those pointers, because the arrangement decides what the container is fast at, what it forbids, and which one you should reach for.

5.2 Lists: an array of pointers

Mental model

A list is one contiguous row of pointer slots in memory, plus a record of how many slots are used (its length) and how many exist (its capacity). Position 3 is found by simple arithmetic (start + 3 slots), so indexing is instant no matter how long the list is.

Consequences you can predict from the picture:

  • items[i] is fast (jump straight to the slot).
  • items.append(x) is fast on average (usually a free slot exists at the end).
  • items.insert(0, x) and items.pop(0) are slow for big lists: every pointer after the position must shift one slot.
  • x in items is slow for big lists: Python checks each slot in turn until it finds a match.

To keep appends cheap, Python over-allocates: when the row is full, it allocates a larger row (with spare slots), copies the pointers over, and frees the old row. Most appends then cost nothing extra. Step through both tabs below: the first shows growth, the second shows a classic bug caused by how for walks a list.

Slicing (items[1:3]) builds a new list of the selected pointers (a shallow copy, Chapter 2). Negative indexes count from the end (items[-1] is the last), and items[::-1] is a reversed copy.

5.3 Tuples: a fixed record

A tuple is an immutable row of pointers. Use one when the items are a small, fixed set of related values (a coordinate, a row, a return of several results) rather than "any number of similar things".

point = (3, 4)
x, y = point                 # unpacking: assigns x = 3, y = 4
a, b = 1, 2
a, b = b, a                  # swap: the right side builds a tuple first, then unpacks
first, *rest = [10, 20, 30]  # first = 10, rest = [20, 30]

single = (5,)                # the COMMA makes a tuple, not the brackets
not_a_tuple = (5)            # just the number 5 in brackets

Functions that "return several values" return one tuple; the caller unpacks it. Because tuples are immutable and hashable (if their contents are), they can be dictionary keys and set members, which lists cannot.

5.4 Dictionaries: a hash table

Mental model

A dictionary is a table of numbered slots. To store or find a key, Python computes the key's hash (a number derived from its value), turns it into a slot number, and looks in that slot. It does not scan the keys. That is why lookups take about the same time in a dictionary of ten entries or ten million.

Two different keys can land on the same slot (a collision). Python then checks whether the key stored there is really the one you asked for (by ==) and, if not, tries another slot by a fixed rule. Step through an insert with a collision:

Two rules follow directly from the mechanism:

  • Keys must be hashable (in practice, immutable): numbers, strings, tuples of hashables. A list cannot be a key. The second tab shows why: if a key's value could change after storing, its hash would change and the dictionary would look in the wrong slot.
  • Equal keys must hash alike, which is why 1, 1.0 and True collapse into a single key (Chapter 4).

Since Python 3.7, dictionaries also remember insertion order. Everyday operations:

prices = {"tea": 30, "coffee": 50}
prices["juice"] = 40               # add or overwrite
print(prices["tea"])               # 30; a missing key raises KeyError
print(prices.get("milk", 0))       # 0; get returns a default instead of raising

    print(name, cost)
merged = prices | {"tea": 35}      # new dict (Python 3.9+); right side wins on clashes

.keys(), .values() and .items() return live views, not copies. And you must not add or remove keys while looping over a dictionary: Python raises RuntimeError: dictionary changed size during iteration. Loop over list(d) if you need to change it as you go.

5.5 Sets: keys with no values

A set is a hash table that stores only keys. It answers "is this in here?" in constant time and guarantees uniqueness. It has no order and no positions.

seen = {"a", "b"}
seen.add("c")
print("a" in seen)                 # True, and fast
print({1, 2, 3} & {2, 3, 4})       # {2, 3}   intersection: in both
print({1, 2} | {2, 3})             # {1, 2, 3} union
print({1, 2, 3} - {2})             # {1, 3}   difference
unique = set([3, 1, 3, 2, 1])      # dedupe (the original order is lost)
empty = set()                      # NOT {}, which is an empty dict

5.6 The performance mental model

You do not need big-O notation, only the difference between "jump" and "scan":

Operationlistdict / set
Get by position / keyJump (instant)Jump (instant, by hash)

Is X in there?Scan (slower as it grows)Jump (instant)

The most common performance bug in real code follows: a membership test if x in big_list inside a loop. With a list of 100,000 items and 100,000 checks that is on the order of ten billion comparisons. Convert the list to a set once (big = set(big_list)) and each check becomes a single jump. Whenever you see in on a list inside a loop, ask whether it should be a set.

5.7 Never change a list while looping over it

The second tab of the illustration showed why. A for loop over a list keeps an index and reads "the item at the next index" each time. If the loop body removes an earlier item, everything shifts left, and the index now points past an item that was never visited. The safe patterns:

nums = [2, 4, 6, 1]
nums = [n for n in nums if n % 2 != 0]     # build a new list of what to keep (Chapter 6)

for n in list(nums):                        # or loop over a COPY and edit the original
    ...

5.8 Reading real code: grouping and lookup

orders_by_customer = {}
for order in orders:
    orders_by_customer.setdefault(order["customer"], []).append(order["id"])

vip = {"c1", "c7"}
big_orders = [o for o in orders if o["customer"] in vip and o["total"] > 1000]

Read it with the picture:

  • orders_by_customer is a dictionary whose values are lists. setdefault(key, []) returns the list stored under the key, first inserting a fresh empty list if the key is missing. The new list is a distinct object each time it is created (compare the default-argument trap, Chapter 2: here the [] is evaluated on every loop pass, so there is no sharing).
  • .append(...) mutates that list in place; nothing is rebound.
  • vip is a set, so o["customer"] in vip is a fast jump, done once per order. Had it been a list, this would be the scan-in-a-loop problem.
  • order["customer"] raises KeyError if any order lacks that key. Noticing where a key access could fail is the first step to reading error handling (Chapter 8).

5.10 Check yourself

Why is my_list[5000] as fast as my_list[2]?

The list is a contiguous row of pointer slots, so Python computes the slot's location directly instead of walking from the start.

Why can a tuple be a dictionary key but a list cannot?

Keys need a stable hash. A tuple's value cannot change, so its hash is stable; a list's value can change, which would change its hash and break lookups. (A tuple that contains a list is unhashable for the same reason.)

What is nums? nums = [1, 2, 3, 4]; for n in nums: if n % 2 == 1: nums.remove(n)

[2, 4] here, but only by luck of the pattern; the loop skipped items after each removal (it visited 1, then the list became [2,3,4] and index 1 gave 3, and so on). The bug shows on other inputs, for example [1, 3, 5] leaves [3].

You test if word in stopwords for every word in a long document. stopwords is a list of 500 words. What is the fix?

Make it a set: stopwords = set(stopwords). Each test becomes one hash jump instead of up to 500 comparisons.

What does d = {}; d["a"] = 1; d["a"] = 2; len(d) return?

1. Keys are unique, so the second assignment overwrote the first value.

Difference between d["x"] and d.get("x") when "x" is missing?

d["x"] raises KeyError; d.get("x") returns None (or the default you pass).

Chapter 6: Control flow, loops and comprehensions

Volume 2: The core language, properly

Control flow is how a program decides what to run next and how many times. Most readers learn if and for as syntax. Here we look at what Python does underneath, because once you see how a for loop actually works, generators, files, database cursors and streaming API responses all turn out to be the same mechanism.

6.1 Statements, expressions and blocks

An expression produces a value (2 + 3, len(items), x if ok else y). A statement performs an action (x = 5, if, for, return). Statements that control flow own an indented block: the lines indented under a colon. Remember Chapter 3: a block groups lines but does not create a new scope.

Python runs statements top to bottom, keeping a marker of "the line I am on". Control flow just moves that marker: skipping ahead (if), jumping back (loops), or diving into another frame (a call).

6.2 Decisions

if score >= 90:
    grade = "A"
elif score >= 75:
    grade = "B"
else:
    grade = "C"

label = "pass" if score >= 40 else "fail"     # conditional expression: a value, not a statement

Conditions are tested top to bottom and only the first true branch runs. The tests use truthiness (Chapter 4), so if items: means "if there is anything in it".

In production code you will see guard clauses: checks at the top of a function that handle bad or trivial cases and return early, so the main logic is not buried in nested indentation.

def average(values):
    if not values:              # guard: nothing to average
        return None
    return sum(values) / len(values)

6.3 What a for loop really does

Mental model

A for loop does not count through the list. It asks a hidden helper, an iterator, for "the next item" over and over, until the helper says "no more". Each answer is bound to the loop variable, then the body runs.

Step through this to see the hidden helper and the loop variable side by side. Then use the other tabs for comprehensions and for...else.

6.4 The iteration protocol: iterable and iterator

Two roles, often confused:

  • An iterable is anything you can loop over: lists, strings, dictionaries, sets, files, range objects. It can hand out an iterator when asked (iter(x)).
  • An iterator is the object that remembers where you are and hands out the next item (next(it)). When it has none left it raises StopIteration, and the for loop quietly treats that as "finished".
it = iter([10, 20])
print(next(it))     # 10
print(next(it))     # 20
print(next(it))     # StopIteration: the iterator is exhausted
print(list(it))     # []   iterators are one-shot: once used up, they stay empty

Looping over a dictionary gives its keys; looping over a file gives its lines; looping over a string gives characters. Whatever object you hand to for, the protocol is identical. That uniformity is why code written for a list often works unchanged on a file or a stream. Chapter 13 shows how to write your own iterators and generators.

6.5 while, break, continue, and the odd else

attempts = 0
while attempts < 3:              # repeats while the condition is truthy
    attempts += 1
    if attempts == 2:
        continue                  # skip the rest of this pass, start the next
    print("try", attempts)

break leaves the loop immediately. while True: with a break inside is the standard shape for "repeat until something happens" (a retry loop, a read loop).

Loops can have an else block, which confuses almost everyone once. The else runs only if the loop finished without hitting break. Read it as "no-break". The third tab in the illustration shows both outcomes. It is used for search loops: "if I never found it, do this".

6.6 range, enumerate, zip: lazy helpers

for i in range(3):                     # 0, 1, 2   the stop value is excluded
    ...
for i, name in enumerate(["a", "b"]):  # (0, 'a'), (1, 'b')   position plus item
    ...
for name, score in zip(names, scores): # pairs items up; stops at the SHORTER input
    ...
big = range(10**9)                     # instant: no billion-item list is created

These return small objects that produce items on demand (they are lazy). range(10**9) stores three numbers (start, stop, step), not a billion of them. Notice also the pattern for i, name in ...: each item is a tuple and the loop unpacks it (Chapter 5). Prefer enumerate over range(len(items)).

6.7 Comprehensions

A comprehension builds a collection from a loop in one expression. The second tab in the illustration shows one running.

big = [n * 2 for n in nums if n > 4]
# exactly the same as:
big = []
for n in nums:
    if n > 4:
        big.append(n * 2)
How to read any comprehension

[ EXPRESSION for ITEM in ITERABLE if CONDITION ]. Read the for part first ("for each item in the iterable"), then the if ("keeping only those where…"), and only then the leading expression ("and make this from each"). The expression is written first but runs last.

squares = {n: n * n for n in range(4)}     # dict comprehension: {0: 0, 1: 1, 2: 4, 3: 9}
unique  = {w.lower() for w in words}       # set comprehension
total   = sum(n * n for n in range(4))     # generator expression: lazy, no list is built
flat    = [x for row in grid for x in row] # nested: the FIRST for is the OUTER loop

A comprehension is a scope of its own (Chapter 3): its loop variable does not leak. Use comprehensions for straightforward "transform / filter" tasks. When the body needs several statements, side effects, or more than one if/for nesting, a plain loop is clearer. Also note the generator expression (... for ...) in brackets or as a sole argument: it produces items lazily, which matters for large data (Chapter 13).

6.8 match: matching shapes

Newer code sometimes uses match (Python 3.10+). It compares a value against patterns, including structure, and can pick the value apart at the same time:

match event:
    case {"type": "click", "x": x, "y": y}:     # a dict with these keys; binds x and y
        handle_click(x, y)
    case ("quit", code):                        # a 2-tuple starting with "quit"
        shutdown(code)
    case [first, *rest]:                        # any non-empty sequence
        ...
    case _:                                     # wildcard: anything else
        ignore()

Read it as a chain of ifs that test shape, top to bottom, first match wins. Names in a pattern (x, y, code) are assigned, not compared.

6.9 Reading real code: cleaning rows, retrying calls

def valid_prices(lines):
    prices = []
    for line in lines:
        if not line.strip():
            continue                          # skip blank lines
        name, _, raw = line.partition(",")
        if not raw.strip().isdigit():
            continue                          # skip malformed rows
        prices.append(int(raw))
    return prices

def wait_until_ready(check, limit=5):
    attempts = 0
    while True:
        if check():
            return True
        attempts += 1
        if attempts >= limit:
            return False

Walk through the first function: lines is any iterable of text (a list, or an open file: same protocol). Each guard continues to the next item, so the last two lines only run for good rows, which keeps the happy path unindented. partition splits at the first comma into three parts, and _ is a conventional name for "a value I will ignore". The list prices is created inside the function and returned, so it survives the frame (Chapter 1). The second function is the standard while True shape with two exits, both returns.

Reading technique: for each loop, name (1) what is being iterated, (2) what the loop variable is on each pass, (3) what the loop accumulates or changes, and (4) every way to leave it.

Chapter 7: Functions in depth

Volume 2: The core language, properly

Functions are where most production code lives, and reading a function signature quickly is the single highest-leverage reading skill. Chapters 1 to 3 gave you the parts: calls make frames, parameters are names, arguments are objects. This chapter puts them together and decodes the alphabet soup of *args, **kwargs, *, / and defaults.

7.1 A function is an object

Executing a def statement creates a function object on the heap and binds a name to it. Nothing inside the body runs yet.

def greet(name, punct="!"):
    return "Hello, " + name + punct

print(type(greet))              # <class 'function'>
print(greet.__name__)           # greet
print(greet.__defaults__)       # ('!',)   the default, stored on the object (Chapter 2)
hello = greet                   # a second label on the same function object
print(hello("Asha"))            # Hello, Asha!
handlers = [greet, len, str.upper]   # functions can sit in lists, be passed and returned

Because functions are ordinary objects, you can store them in containers, pass them into other functions, and return them from functions. Much of the AI-builder stack (callbacks, tool registries, decorators, pipelines) depends on exactly this.

7.2 Parameters and arguments, and how they are matched

Parameters are the names in the def line. Arguments are the objects supplied at the call. When you call a function, Python matches arguments to parameters in a fixed sequence:

  1. Positional arguments fill parameters left to right.
  2. Keyword arguments (name=value) fill parameters by name.
  3. Any parameter still unfilled takes its default, if it has one; if it has none, that is a TypeError.
  4. Extra arguments either go to catch-all parameters (*args, **kwargs) or are a TypeError.

Each bound parameter is an assignment of a name in the new frame to the argument's object, exactly as in Chapter 2. Nothing is copied.

7.5 Return values

return ends the call, pops the frame, and hands one object back. "Returning several values" returns one tuple, which the caller usually unpacks. A function that reaches its end without return (or with a bare return) gives back None.

def min_max(values):
    return min(values), max(values)      # one tuple

lo, hi = min_max([4, 9, 1])              # unpacked: lo = 1, hi = 9

7.6 Defaults, once more

Chapter 2's rule again, because it matters in signatures: defaults are evaluated once, at def time, and stored on the function object. A default that is a fresh number, string, tuple or None is safe. A default that is a list, dict or set is shared across calls. Also, a default computed from another name captures that name's value at the moment of def, not at call time:

import time
def log(msg, when=time.time()):    # evaluated ONCE: every call reports the same timestamp
    ...
def log(msg, when=None):           # the fix: compute it inside
    when = when if when is not None else time.time()

7.7 Functions as values

Since a function is an object, you can pass it where a value is expected. The receiving code calls it whenever it likes:

words = ["pear", "fig", "banana"]
print(sorted(words, key=len))          # ['fig', 'pear', 'banana']  key: "call this on each item to get its sort value"
print(list(map(str.upper, words)))     # apply a function to each item

ops = {"add": lambda a, b: a + b, "mul": lambda a, b: a * b}
print(ops["mul"](3, 4))                # 12    a dispatch table: look up a function by name, then call it

A lambda is a tiny unnamed function limited to one expression: lambda a, b: a + b is the same as a def that returns a + b. Use it for short throwaway callbacks; use def when it needs a name, several lines or a docstring. Dispatch tables like ops replace long if/elif chains and are common in command handlers and tool registries.

7.8 Anything callable

The call syntax thing(...) works on any callable object, not just functions. Classes are callable (calling one builds an instance: Chapter 15), and any object whose class defines __call__ is callable too. So when reading foo(x) you cannot assume foo is a function. 7.10 Reading real code: a wrapper that forwards its options

def request(method, url, *, params=None, headers=None, timeout=10, verify=True):
    ...

def fetch(url, **options):
    return request("GET", url, **options)

fetch("api.example.com/data", timeout=5, verify=False)

Decode it:

  • request has two positional parameters, then a bare *, so params, headers, timeout and verify are keyword-only, each with a default.
  • fetch takes one URL and **options: any keyword arguments the caller passes are collected into a dictionary.
  • Inside, **options at the call site unpacks that dictionary back into keyword arguments for request. So the call is identical to request("GET", url, timeout=5, verify=False).

This "collect and forward" pattern appears constantly: wrappers, decorators (Chapter 12), and library layers that add a convenience on top of a more general function. Its cost is visible in the signature: fetch no longer tells you what options exist. You must read request to know. The fourth tab in the illustration shows this one being bound.

Errors and exceptions: what happens when a call fails, how an error travels up the call stack you now know, and how to read a traceback.

Chapter 8: Errors and exceptions

Volume 2: The core language, properly

Programs fail: a file is missing, a key is absent, a network call times out, a user types letters where numbers belong. What matters is what happens next. Python's mechanism is the exception, and it is built directly on the call stack from Chapters 1 and 3. Once you can picture an exception travelling up the stack, tracebacks and error handling stop being mysterious.

8.1 What an exception is

An exception is an object (an instance of an exception class) that Python creates when something goes wrong, or that you create yourself with raise. It carries a type (ValueError), a message, and the record of where it happened. Two very different kinds of failure exist:

  • Syntax errors: the file cannot even be read as Python (a missing colon). They are reported before anything runs.
  • Exceptions: the code is valid but a line fails while running. Only these can be caught and handled.

8.2 try, except, else, finally

try:
    value = int(text)              # 1. attempt the risky operation
except ValueError as err:          # 2. runs ONLY if a ValueError was raised in the try block
    print("not a number:", err)
    value = 0
else:                              # 3. runs ONLY if the try block raised nothing
    print("parsed fine")
finally:                           # 4. ALWAYS runs, error or not
    print("done")

8.3 Watch an exception travel

Mental model: unwinding

When an exception is raised, Python stops the current line and looks for a matching except in the current frame. If there is none, that frame is discarded and the same exception is raised in the caller's frame at the line where it made the call. This repeats up the stack. If a matching handler is found, execution resumes there. If the bottom of the stack is reached with no handler, the interpreter prints the traceback and exits.

Step through three cases: an exception handled two levels up, one nobody handles, and finally running during unwinding.

The traceback Python prints in the unhandled case is a record of the frames the exception passed through, in call order. It is the stack from Chapter 1, made visible: read it from the bottom (the error and where it happened) upward (who called whom).

8.4 The exception family tree, and how matching works

Exception classes form a hierarchy, and except X catches X and every subclass of X. The parts you need:

BaseException
 +-- KeyboardInterrupt, SystemExit         # Ctrl-C and sys.exit(): do not catch these casually
 +-- Exception                             # everything you normally handle is below here
      +-- ArithmeticError  -> ZeroDivisionError
      +-- LookupError      -> KeyError, IndexError
      +-- ValueError                       # right type, unacceptable value: int("abc")
      +-- TypeError                        # wrong type: "a" + 1
      +-- AttributeError                   # object has no such attribute
      +-- NameError        -> UnboundLocalError
      +-- OSError          -> FileNotFoundError, PermissionError, TimeoutError
      +-- ImportError      -> ModuleNotFoundError
      +-- RuntimeError     -> RecursionError
      +-- StopIteration                    # iterator exhausted (Chapter 6)

Practical consequences:

  • except LookupError catches both a bad list index and a missing dict key.
  • except Exception catches nearly everything, so it is a blunt instrument. A bare except: is worse: it also catches KeyboardInterrupt, so Ctrl-C stops working.
  • Handlers are tested in order; the first match wins. Put the specific ones first: catching Exception before KeyError makes the second unreachable.
  • You can catch several at once: except (KeyError, ValueError) as err:.

8.5 Raising, re-raising, chaining, and your own exceptions

def set_age(age):
    if age < 0:
        raise ValueError(f"age must be non-negative, got {age}")   # signal the problem
    return age

try:
    config = load(path)
except FileNotFoundError as err:
    raise RuntimeError("cannot start: config missing") from err    # chaining: keeps the cause

try:
    risky()
except Exception:
    log("risky failed")
    raise                                  # bare raise: re-raise the SAME exception, traceback intact

class ConfigError(Exception):              # your own type: a subclass of Exception
    pass

raise NewError(...) from err records that NewError was caused by err. When you read a traceback that says "The above exception was the direct cause of the following exception", you are reading a chain: the first block is the root cause, the last is what the caller finally saw. Read from the first. Custom exception classes let callers catch your library's failures specifically without also catching unrelated ones.

8.6 Ask forgiveness, or ask permission

Two styles exist for the same job:

# "Look before you leap" (LBYL): check first
if key in data:
    value = data[key]
else:
    value = None

# "Easier to ask forgiveness than permission" (EAFP): try, and handle failure
try:
    value = data[key]
except KeyError:
    value = None

# for this particular case there is a shorter idiom still
value = data.get(key)

Python culture leans toward EAFP, partly because checking first can be wrong: for a file, someone can delete it between your exists() check and your open(). Trying, then handling failure, is the only reliable test. Use whichever reads more clearly, and prefer the specific idiom (get) when it exists.

8.7 Handling errors well

  • Catch the narrowest type you can, around the smallest amount of code. A try wrapping fifty lines will hide bugs in the other forty-nine.
  • Never swallow silently. except Exception: pass turns a crash you could diagnose into wrong results you cannot. At minimum, log the error with its traceback.
  • Handle an error where you can do something useful about it. Low-level functions usually let exceptions rise; a higher layer (the request handler, the main loop) decides to retry, show a message, or give up.
  • Cleanup goes in finally (or a with block, Chapter 14). Do not put return inside finally: it silently discards any exception in flight.

Two smaller tools. assert condition, "message" checks an internal assumption and raises AssertionError, but assertions can be switched off entirely (with python -O), so never use them to validate user input. And warnings (warnings.warn) report a problem without stopping the program.

8.8 Reading real code: retry with a cause

import time

def fetch_with_retry(fetch, attempts=3, delay=1.0):
    last_error = None
    for attempt in range(attempts):
        try:
            return fetch()
        except (TimeoutError, ConnectionError) as err:
            last_error = err
            time.sleep(delay * (2 ** attempt))      # wait 1s, then 2s, then 4s
    raise RuntimeError(f"gave up after {attempts} attempts") from last_error

Decode with the chapter:

  • fetch is a function passed in as an argument (Chapter 7); the retry logic does not care what it does.
  • A successful fetch() hits return, which leaves the whole function, so the loop needs no explicit success handling.
  • Only TimeoutError and ConnectionError are caught. Any other exception (a ValueError from bad data, say) is not retried: it unwinds straight to the caller, which is right, since retrying will not fix bad data.
  • last_error = err copies the exception into a name that outlives the except block (Python deletes err itself at the end).
  • If the loop finishes without returning, all attempts failed. The new RuntimeError is raised from last_error, so the traceback keeps the underlying cause. The for loop's normal exit, not a break, is what leads to the raise.

8.10 Check yourself

A function raises KeyError and its caller has except LookupError:. Is it caught?

Yes. KeyError is a subclass of LookupError, and except matches subclasses.

What is printed? try: print("a") except: print("b") else: print("c") finally: print("d")

a, c, d. No exception, so else runs; finally runs last.

Why is putting 40 lines inside one try a problem?

A matching exception from any of them is treated as the expected failure, hiding unrelated bugs. Wrap only the statement that can fail.

It re-raises the exception being handled, unchanged, with its original traceback.

It silently discards every error, so failures show up later as wrong results with no trail. Catch narrowly and log.

level3 and level2, in that order. Execution resumes in level1, in its except block.

Files, paths, JSON, CSV and environment variables: how your program talks to the world outside its own memory.

Chapter 9: Files, paths, JSON, CSV and environment variables

Volume 2: The core language, properly

Everything so far lived in memory and vanished when the program ended. Real programs read settings, load data, and save results, which means talking to the world outside the process: files, folders, environment variables. This chapter is about the boundary, and the mental model is simple: outside data must be brought into your program's memory as objects, and anything you want to keep must be written back out.

9.1 Two worlds: memory and disk

Your objects live on the heap and disappear when the process exits. Disk files persist, but Python cannot use them directly: it has to open them, read bytes into objects (strings, lists, dictionaries), work on those objects, and write results back. Three consequences follow: reading and writing are slow compared with memory access, files can be huge (larger than memory), and the outside world is untrusted: a file can be missing, malformed, locked, or in an unexpected encoding. Chapter 8's exceptions are your tool for those cases.

9.2 A file object is a handle

Mental model

open() does not load the file. It asks the operating system for access and returns a file object (a handle): an object holding a connection to the file, a cursor (the current position), and a small buffer. Reading moves the cursor forward. Writing goes into the buffer first and reaches the disk when the buffer is flushed or the file is closed.

Step through reading a file line by line, then the two things that surprise people when writing, then the folder trap.

The modes you will see: "r" read (default), "w" write and truncate (empty the file immediately), "a" append, "x" create and fail if it exists, plus "b" for bytes ("rb", "wb") and "+" for read and write. The three ways to read text:

text  = f.read()        # the whole file as ONE string: fine for small files only
line  = f.readline()    # one line (including its "\n")
for line in f:          # iterate line by line: only one line in memory at a time
    ...

A file object is an iterator (Chapter 6): for line in f uses the very same protocol as looping over a list. That is why code that processes a list of lines usually works unchanged on an open file, and why a 20 GB log can be scanned with a few kilobytes of memory.

9.3 with: guaranteed closing

An open handle holds an operating-system resource, and unflushed data may not be on disk yet. You must close it, even if an exception happens. The with statement does that:

with open("prices.txt", encoding="utf-8") as f:
    data = f.read()
# here f is closed, whether the block finished normally or raised

with is essentially a try/finally that calls f.close() for you (Chapter 8's finally). Chapter 14 explains the general mechanism, which also manages locks, database connections and network sessions. Always open files with with.

9.4 Text, bytes and encodings

Disk files hold bytes. In text mode, Python decodes them into str using an encoding (Chapter 4). If you do not say which, Python uses a platform default that varies between machines, and a file that works on your laptop may fail or turn into garbage ("mojibake") on a server. So always be explicit:

open("notes.txt", encoding="utf-8")                  # read text
open("out.txt", "w", encoding="utf-8")               # write text
open("image.png", "rb")                              # bytes: no decoding, no encoding argument

9.5 Paths: pathlib and the working-directory trap

A path is a description of where a file is. Use pathlib.Path, which treats paths as objects and overloads / (Chapter 4's operator dispatch) to join them on any operating system:

from pathlib import Path

base = Path("data")
report = base / "2024" / "sales.csv"      # data/2024/sales.csv (uses the right separator per OS)
print(report.name, report.stem, report.suffix, report.parent)
                                          # sales.csv  sales  .csv  data/2024
if report.exists():
    text = report.read_text(encoding="utf-8")
report.parent.mkdir(parents=True, exist_ok=True)   # create folders if missing
for csv_file in base.glob("**/*.csv"):     # find files by pattern, recursively
    ...

The trap: a relative path ("data.csv", Path("data")) is resolved against the current working directory: the folder you were in when you launched the program, not the folder containing the script. The last tab of the illustration shows the same script working from one folder and failing from another. To locate files relative to the script itself, anchor on __file__:

BASE = Path(__file__).resolve().parent
config_path = BASE / "settings.json"       # works no matter where the program is launched from

9.6 JSON: text that maps onto Python objects

JSON is the near-universal format for exchanging structured data (files, web APIs, LLM tool calls). It is text whose structure matches Python's basic types:

JSONPython
object {"a": 1}dict
array [1, 2]list
string, numberstr, int or float
true / falseTrue / False
nullNone
 
import json

data = json.loads('{"name": "Asha", "scores": [90, 85], "active": true}')   # text -> objects
print(data["scores"][0])           # 90
text = json.dumps(data, indent=2)  # objects -> text

with open("out.json", "w", encoding="utf-8") as f:
    json.dump(data, f)             # (no s) write straight to a file
with open("out.json", encoding="utf-8") as f:
    again = json.load(f)           # (no s) read from a file

Remember: loads/dumps work on strings (the "s"), load/dump on files. JSON is a lossy round trip. Tuples become arrays and come back as lists; dictionary keys always become strings ({1: "a"} returns as {"1": "a"}); and sets, dates and your own objects are not serializable (TypeError: Object of type set is not JSON serializable) until you convert them.

9.7 CSV: rows of text

import csv

with open("sales.csv", newline="", encoding="utf-8") as f:
    for row in csv.DictReader(f):          # each row becomes a dict keyed by the header line
        amount = float(row["amount"])       # EVERY value is a string: convert it yourself

The csv module handles quoting and commas inside fields for you (do not split on commas by hand). The recurring gotcha, repeated from Chapter 4: everything read from a file is text. Numbers, dates and booleans need explicit conversion, and that conversion can fail (Chapter 8), so decide where bad rows go.

9.8 Environment variables and configuration

Every process inherits a set of environment variables: named text settings supplied by the shell, the operating system, or a deployment platform. In Python they appear as os.environ, a dictionary-like object whose values are always strings:

import os

os.environ["HOME"]                      # KeyError if missing
os.getenv("API_URL", "http://localhost")  # default if missing; returns a str (or your default)
port = int(os.getenv("PORT", "8000"))     # convert at the boundary (Chapter 4)

Configuration through the environment is the standard way to change behaviour between your laptop, a test server and production without editing code, and the standard place for secrets (API keys, database passwords). Never hard-code a secret in source or commit it to version control. During development a .env file (loaded by a helper library such as python-dotenv) fills the environment for you; that file must stay out of the repository.

9.9 Big files and safe writes

  • Stream, do not slurp. f.read() on a multi-gigabyte file exhausts memory. Iterate lines, or read fixed-size chunks with f.read(65536).
  • A crash mid-write can leave a half-written file. For important files, write to a temporary file in the same folder, then swap it in with os.replace(tmp, final), which replaces the target in one step.
  • "w" destroys the old contents the moment it opens, before you write a byte (second tab of the illustration). Use "a" to add to the end, or "x" to refuse to overwrite.

9.10 Reading real code: a settings loader

import json
import os
from pathlib import Path

BASE = Path(__file__).resolve().parent

def load_settings():
    path = Path(os.getenv("APP_CONFIG", BASE / "settings.json"))
    with path.open(encoding="utf-8") as f:
        data = json.load(f)
    data["debug"] = os.getenv("DEBUG", "0") == "1"
    return data

Walk through it, object by object:

  • BASE is a Path object computed once when the module loads, anchored on the script's own location (so it is immune to the working-directory trap).
  • os.getenv("APP_CONFIG", BASE / "settings.json") returns a string if the variable is set, or the default Path if not. Wrapping the result in Path(...) makes both cases the same type. That is a small but deliberate normalisation.
  • path.open(...) returns a file handle. The with block guarantees it is closed. json.load(f) reads the text from the handle and builds a dict on the heap. After the block, f is closed but data lives on.
  • os.getenv("DEBUG", "0") == "1" compares two strings and produces a real bool. This is the correct version of the buggy pattern in Chapter 4.9: the value is converted at the boundary.
  • Possible failure points, which you can now spot: a missing file (FileNotFoundError), invalid JSON (json.JSONDecodeError, a ValueError subclass), and the file being valid JSON but not an object (then data["debug"] = ... raises TypeError).

Modules, imports and packages: how one Python file uses another, where Python looks for it, and what really happens when you write import.

Chapter 10: Modules, imports and packages

Volume 2: The core language, properly

No real program is one file. The moment code is split across files, you need to know how one file uses another, where Python goes looking, and what runs when. This chapter closes Volume 2, and it rests on Chapter 3: a module is a namespace, and import is a way of building one and pointing a name at it. It also explains the most common error messages new engineers hit (ModuleNotFoundError, "cannot import name", "attempted relative import").

10.1 What a module is

Mental model

A module is a Python file that has been run once, top to bottom, with everything it defined (names for functions, classes, constants) collected into a module object: a namespace table exactly like the global namespace of Chapter 3. Importing a module means getting a name in your file that points at that object.

This has an immediate consequence that trips people up: the top-level code of a module runs at import time. If a file contains print("loading") or connects to a database at the top level, that happens the first time anyone imports it. Files that are meant to be imported should mostly contain definitions, not actions.

10.2 What happens when you write import util

  1. Check the cache. Python keeps a dictionary called sys.modules of every module already loaded. If "util" is there, use that object and stop.
  2. Search. Otherwise, walk the list sys.path (a list of folders) in order, looking for util.py or a util/ package. First match wins.
  3. Create and register. Make an empty module object and store it in sys.modules["util"] (before running any of its code).
  4. Execute. Run the file's code from top to bottom inside that module's namespace.
  5. Bind. Create the name util in your namespace, pointing at the module object.

Watch each of these, then the package case, the "from" trap, and the circular-import failure.

The cache is why importing the same module twice is cheap and why its top-level code runs only once per program: every file in your project that writes import util gets the same module object, so module-level variables act as shared state.

10.3 The import forms, and what each one binds

import util                 # binds ONE name: util  -> the module object.   Use: util.VERSION
import util as u            # same, but the name is u
from util import VERSION    # binds VERSION -> the object that util.VERSION points at, right now
from util import *          # binds every public name from util into your namespace: avoid

The subtle one is from util import VERSION. It does not keep a live link. It looks the name up once and points your own label at whatever object it found (Chapter 2: assignment attaches labels). If util later re-points its VERSION at a different object, your VERSION still points at the old one. Third tab of the illustration. The practical rule: when the value may change at run time (settings, flags), import the module and read util.NAME each time; import the name only for things that do not change (functions, classes, constants).

from util import * makes it impossible to tell where a name came from and can silently overwrite your own names (Chapter 3's shadowing). Avoid it in real code.

10.4 sys.path and the shadowing trap

sys.path is an ordinary list of folder names. When you run a script, the first entry is the folder containing that script; then come any folders in the PYTHONPATH environment variable, then the standard library, then the folder where third-party packages are installed (site-packages). You can print it: import sys; print(sys.path).

Because the search is in order and first match wins, a file you create can shadow a real module of the same name. If your project has a file called random.py, json.py, email.py or test.py, then import random finds your file first, and standard-library code that needs the real one breaks in bewildering ways ("module has no attribute…", "partially initialized module"). Never name your files after standard-library or installed modules.

10.5 Packages

A package is a folder of modules. Historically it must contain a file named __init__.py (which may be empty) to mark it as a package:

shop/
    __init__.py       # runs when "shop" is imported; often empty or re-exports names
    cart.py
    pricing/
        __init__.py
        tax.py

import shop.cart               # module object for shop, then for shop.cart
from shop.pricing import tax   # the tax module
from shop.cart import add      # the function add from cart.py

Importing shop.cart imports shop first (running shop/__init__.py), then shop.cart (running cart.py), and makes cart an attribute of the shop module object. The name bound in your file is only the top one, shop, as the second tab shows. Dotted access (shop.cart.add) simply walks attribute lookups from module to module.

Because __init__.py runs on import, packages often use it to give a tidy public surface: from .cart import add inside shop/__init__.py lets users write from shop import add. When you meet an unfamiliar package, its __init__.py is the first file to read.

10.6 Absolute and relative imports, and the -m rule

from shop.pricing import tax     # absolute: full path from a folder on sys.path
from .cart import add            # relative: "cart, in the SAME package as this file"
from ..utils import clean        # relative: "utils, one package level up"

A leading dot means "relative to the package this file belongs to". That only makes sense if Python knows the file is part of a package. If you run such a file directly as a script (python shop/cart.py), Python treats it as a lone top-level file with no package around it, and you get ImportError: attempted relative import with no known parent package. Run it as a module instead, from the folder above the package: python -m shop.cart. Seeing relative imports in a file tells you it is meant to live inside a package and be launched with -m or imported by other code.

10.7 if __name__ == "__main__":

Every module has a built-in name __name__. If the file was run directly, __name__ is the string "__main__". If it was imported, __name__ is the module's name ("util"). The guard uses that to separate "importable definitions" from "what happens when launched":

def main():
    ...

if __name__ == "__main__":     # True only when launched: python util.py
    main()                     # NOT run when another file does "import util"

Without the guard, importing the file would run main() as an unwanted side effect (recall 10.1). With it, the same file works as a reusable library and as a runnable program.

10.8 Circular imports

If a.py imports b and b.py imports a, each needs the other before it has finished loading. Because a module is registered in sys.modules before its code runs (step 3), the second file finds a half-built module and may ask for a name that does not exist yet: ImportError: cannot import name 'A_VAL' from partially initialized module 'a' (most likely due to a circular import). The last tab traces it. Common fixes, best first: restructure so the shared piece lives in a third module that both import; import the module (import a) instead of names from it and use a.A_VAL later, at call time; or, as a last resort, do the import inside the function that needs it.

10.9 Cost, side effects and __pycache__

  • Importing runs code, so heavy imports (large libraries) slow start-up. Some programs import a rarely used library inside the function that needs it to keep start-up fast.
  • Python saves the compiled form of each imported module in a __pycache__ folder as .pyc files, so later starts skip recompiling. It speeds start-up, not running; delete the folder safely at any time, and keep it out of version control.
  • Editing a module while a program runs does not update it: the cached module object is already built. Restart the program (or, in a notebook, use importlib.reload).

10.10 Third-party packages

Code other people wrote (requests, fastapi, langchain) is installed with pip into a folder called site-packages, which is on sys.path. Two habits prevent most confusion. First, the pip command and the python command can belong to different Python installations, so use python -m pip install ... to be sure they match. Second, ModuleNotFoundError almost always means "the Python running this code is not the Python you installed into". Print sys.executable to see which one it is. Chapter 19 (virtual environments) makes this systematic.

10.11 Reading real code: where does each name come from?

import json
from pathlib import Path

import httpx
from fastapi import FastAPI

from .config import settings
from . import utils

app = FastAPI()

def main():
    data = json.loads(Path(settings.path).read_text())
    return utils.summarize(data)

    main()

Trace every name to its source:

  • The first group is the standard library (json, pathlib); the second is third-party (httpx, fastapi, found in site-packages); the third is this project (leading dots). That three-group order is a convention, and it lets you see at a glance what the file depends on.
  • from .config import settings: relative import, so this file is inside a package; settings is an object defined in the sibling module config.py. Because it is imported by name, it will not reflect the module re-pointing settings later. Fine if settings is an object that is mutated, not replaced.
  • from . import utils imports the sibling module itself, so utils.summarize is an attribute lookup on it.
  • httpx is imported but never used in the excerpt. That is a hint (a leftover import, or used in code not shown), and linters flag it.
  • The guard means main() runs only when launched. And because of the relative imports, launching means python -m package.module, not python file.py.

The general technique: for any name, find its binding statement in this file (def, an assignment, or an import). If it is an import, follow it to the other file and repeat.
